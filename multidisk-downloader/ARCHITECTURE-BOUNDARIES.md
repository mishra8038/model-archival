# Architecture boundaries: selector vs downloader/uploader

## Goal

Keep model selection completely separate from transfer execution.

---

## Subsystems

1. Selector/Planner
- Inputs: registries, priorities, policy overrides, drive allocation policy, budget constraints.
- Output: `transfer-plan.json` (versioned, immutable per run).
- Responsibilities: decide *what* to transfer and *in what order*.

2. Downloader Engine
- Input: `transfer-plan.json` download items.
- Responsibilities: fetch and verify bytes to local storage.
- Non-responsibilities: selecting new models, editing priorities, reading selector registries for decisions.

3. Uploader Engine
- Input: `transfer-plan.json` upload items or upload roots generated by selector.
- Responsibilities: copy verified local artifacts to remote destinations.
- Non-responsibilities: selecting upload candidates from policy registries.

---

## Mandatory boundary rules

B-1: No direct imports from selector modules into downloader/uploader core workers.

B-2: Downloader/uploader can depend on shared utility libraries only (logging, state I/O, hash, retries), not selector policy libraries.

B-3: Selector emits concrete destination paths; downloader/uploader do not perform drive-placement decisions.

B-4: Selector determines item inclusion/exclusion; downloader/uploader cannot add/remove items.

B-5: Emergency/manual overrides must modify selector output (plan/override files), not transfer-worker selection logic.

B-6: CI checks should fail if transfer packages reference selector-only config files (for example registry files) directly.

---

## Data contracts

Minimum plan item fields:

- `item_id`
- `action` (`download` or `upload`)
- `source` (repo/path/revision or local path)
- `destination` (drive alias + absolute/relative target path)
- `verification` (hash/manifest mode)
- `retry_policy`
- `priority_hint`

The contract must include:

- `plan_version`
- `created_at`
- `created_by` (selector build/version)
- optional `overrides_version`

---

## Runtime model

- Selector runs first and writes a plan artifact.
- Downloader/uploader start with plan validation.
- Worker loops consume plan entries only.
- Between items, workers may reload selector-provided override files (priorities, pause lists) but never recalculate candidate sets from registries.

---

## Auditability

Each transfer event should include:

- `plan_version` and `item_id`
- action + outcome
- bytes moved, duration, average throughput
- verification result
- terminal status and error category (if any)

This ensures that outcomes can be traced to selector decisions without coupling transfer engines to selector internals.
